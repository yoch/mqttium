# Transport, reactor and recovery review

Reviewed `mqttiumd` at `49bbaaa4d1d080f458980e3498e90638e317668d` for PR 648. The review found one P1 and two P2 issues. The P1 is a feasible production interleaving established by source inspection. Timing and frequency remain unmeasured. This was a read-only review of the checkout and GitHub state.

## P1 · MQTT DISCONNECT can discard the write fact that completes an acknowledged QoS 1 delivery

**Reachability.** An authenticated subscriber keeps a persistent session and receives an expiring QoS 1 PUBLISH. The TLS task publishes `Written::Started` after its first positive ciphertext write, and publishes `WireProgress` and `Written::Complete` after its last positive write. It subsequently forwards ordinary inbound MQTT packets. Both those receipts and a valid PUBACK followed by ordinary MQTT DISCONNECT can therefore be waiting when the reactor polls the peer. The reactor consumes up to four inbound messages before it reads the written lane. The outbound PUBACK target is already registered for this precise claim and frame before socket submission. This is an authenticated, policy-authorized path in the normal binary and needs neither malformed input nor storage failure. [TLS task](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/net/tls.rs#L456) · [Reactor lane order](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L2654) · [Write receipt poll](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L2718) · [PUBACK binding](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L4082)

**Failure.** The reactor freezes the PUBACK target when it dequeues the inbound packet. The following MQTT DISCONNECT drains owner inputs and immediately calls `close`. The owner records `early_puback` for expiring deliveries with an unmarked claim, so that transition alone cannot submit `FinishDelivery`. `close` removes the `Peer` and pending frame, generates `Failed`, and moves the transport to `retiring`, which only joins the task. A real Started receipt sitting in the peer’s channel is lost even if the peer read and acknowledged the entire PUBLISH. `wire_progress` only releases matching inbound receive credit, so its presence does not persist an outbound Started marker. The special TLS terminal path applies frame results before logical close on `Incoming::Closed`/TLS EOF, but the valid MQTT DISCONNECT branch bypasses it. Orderly process shutdown also calls `close` for all peers before its first connection poll, so the same receipt-loss mechanism warrants coverage there. [Frozen ACK](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L2553) · [MQTT DISCONNECT](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L2440) · [Early ACK state](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner/pubsub.rs#L1355) · [Peer and frame retirement](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L625) · [TLS close drain](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L2853) · [Wire progress](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L2920) · [Orderly shutdown](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L739)

**Consequence.** A legitimately acknowledged delivery can keep its durable obligation, payload reference and packet identifier. The caller may resume while the lifetime is still established fresh and cause another attempt. After expiry an unmarked claim is ineligible for replay, closing clears the owner’s claim-level certainty, and the regular SQLite sweep preserves claimed rows. With infinite Session Expiry this can pin capacity until explicit session termination or replacement. A finite session’s eventual expiry can clean it up. The affected outcome is a durable availability and accounting inconsistency. An interleaving in which Started already reached the owner can complete correctly. The impact is not a confirmed live-run failure or a measured frequency. [Send and cleanup predicates](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner/pubsub.rs#L93) · [Close invalidates certainty](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner/pubsub.rs#L528) · [Exact frame guard](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner/pubsub.rs#L2481) · [Sweep preserves claims](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/message_expiry.rs#L320) · [Recovered claim test](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner/pubsub.rs#L5953)

**If the durable Started result arrives after disconnect.** Once the exact `MarkDeliveryStarted` operation has been submitted, an already-applied early PUBACK and a later known Started commit can finish the surviving offline delivery in the same process. The result checks the exact operation, effect and facts, and the owner can schedule Finish immediately or from reserved control work. The defective interleaving never submits that operation because it drops the receipt. A restart has no durable early-PUBACK bit. A recovered claim with a durable Started marker is eligible for QoS 1 replay with the original packet identifier and can finish on a fresh PUBACK. [Committed Start to Finish](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner/pubsub.rs#L2093) · [Offline control continuation](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner.rs#L1955) · [Recovered metadata](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner/pubsub.rs#L150)

**Minimal correction and regression.** Record valid DISCONNECT and freeze its close intent immediately. Stop admitting new packets from that peer and let the reactor collect and apply pending exact frame facts before retiring owner authority for the generation. Keep the close and receipt drain bounded, and preserve exact correlation on the existing queues. A positive-protocol regression can use one normal mTLS persistent subscriber and one expiring QoS 1 PUBLISH. Synchronize the test reactor so it polls only after the real transport has queued its Started receipt and the subscriber’s ordinary PUBACK and MQTT DISCONNECT. Check for `connection_closed` with `client_disconnect` on the original generation and for `core_finish_observed` on the same delivery identity recorded by `frame_queued`. Inspect SQLite for that exact claim and obligation to disappear while the session remains. This distinguishes Finish, session cleanup and a merely closed socket. Current adjacent tests cover a nonexpiring clear-text publication that can Finish without Started, and a TLS publication for which Started was already observed before the test’s PUBACK. [Clear-text ACK/DISCONNECT test](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime_tests.rs#L598) · [TLS fragmented test](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/tests/system/secure_reception.py#L550) · [Finish diagnostic](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L1432)

## P2 · A sealed TLS frame can age while still fresh and lose its exact zero-byte outcome

The TLS task seals the first remaining-interval value into ciphertext and rechecks that value before its first successful write. With an interval of multiple seconds, a normal delay across an elapsed-second boundary can lower the advertised value while the message remains fresh. This can occur after a zero-progress socket write or if the task is descheduled between sealing and its first attempt. The task returns `tls_expiry_value_aged` at offset zero. Closing that TLS connection is required once the sealed records’ sequence numbers have been consumed. The aged branch, unlike the established-expired branch beside it, emits no correlated zero-byte receipt for the active frame. `Task::run` reports failures only for frames still in its queue, and the runtime later substitutes a generic failure for this active frame. On a fresh unstarted claim the core then loses certainty it actually had, so ordinary expiry may leave the claim and reference charged after the lifetime if the subscriber has stayed offline. This requires both a rounding-boundary crossing before positive progress and a still-unstarted claim. The connection-close policy itself is documented. [Patch and seal](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/net/tls.rs#L342) · [Aged branch](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/net/tls.rs#L416) · [Task cleanup](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/net/tls.rs#L243) · [Rounding](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-contract/src/message_expiry.rs#L58) · [Transport decision](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/docs/decisions/0035-private-mtls-profile.md#L71)

Carry an exact, correlated zero-byte transport refusal into the owner before closing on an aged sealed frame. Give that reason a meaning distinct from expiration and temporal uncertainty, preserve the claim’s original lifetime and earlier-attempt uncertainty, and allow reclamation only once the owner independently observes established expiry. Add a test that crosses a rounding boundary earlier than the deadline, establishes zero positive writes, observes close, and checks known-unsent cleanup at the original deadline. The current sealed TLS test waits past the whole one-second lifetime and only covers `Expired`. [Owner zero-byte handling](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-core/src/owner/pubsub.rs#L2520) · [Sealed TLS test](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/tests/system/secure_reception.py#L524)

## P2 · Keep Alive uses reactor processing time as the reception timestamp

Both readers construct a complete-frame observation before bounded queueing. That BOOTTIME observation is used for Message Expiry. Keep Alive instead resets `last_packet` with `Instant::now()` after the reactor dequeues and decodes each valid packet. The timeout is checked after incoming packets are processed. If the reactor polls after the 1.5× deadline and a valid packet arrived after that deadline but before that poll, its processing refreshes the timer and the overdue generation stays open. A lawful packet already queued can also shift the next deadline by its residence time. Timing depends on scheduling or backpressure. The normal loop attempts to poll every millisecond, and this finding does not imply a uniform delay bound. [TLS frame completion](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/net/tls.rs#L86) · [TCP frame completion](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/net.rs#L432) · [Timer reset](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L2407) · [Timeout order and threshold](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L2870) · [Main loop](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L4733)

Carry a complete-frame monotonic arrival time to the reactor and compare it with the prior peer deadline before advancing the timer. Apply timely queued packets in order and leave partial packets without Keep Alive credit. Test a timely complete packet and a late complete packet across the same deliberately delayed reactor turn, with the negotiated deadline and close generation correlated. The clear-text reception checks regular PING and then idle closure. The mTLS measurement records one idle Keep Alive to Will sample, and its elapsed assertion is at least one second from before opening the connection through Will receipt. Neither distinguishes socket arrival from reactor dequeue at the 1.5× boundary. [Clear-text PING/idle case](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/tests/system/tcp_reception.py#L279) · [Keep Alive sample](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/tests/system/secure_reception.py#L661)

## Integration and evidence boundaries

- The normal listener selects the bounded TLS task when security is configured. It uses one nonblocking rustls task per socket and the same runtime and pure owner as clear-text. TLS negotiates full TLS 1.3 before installing its immutable principal. The reactor checks ClientID and Will authorization before looking for an old attachment or allocating Open. It authorizes business packets before queuing core work.
