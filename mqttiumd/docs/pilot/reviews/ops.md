# mqttiumd pre-pilot review · D · Operations and storage

Candidate `49bbaaa4d1d080f458980e3498e90638e317668d` (PR 648). The findings distinguish the packaged private-network pilot from the direct CLI and from boundary cases on induced SQLite layouts. I found no demonstrated committed-state loss in the packaged, single-path pilot. I would gate that pilot on the host, storage and restore checks below. The CLI path-collision risk warrants a fix before offering arbitrary event-file configuration as a supported operating mode.

## Findings

**P1 · Database and WAL space depend on host controls.** The live writer limits slots and the logical size of broker objects. Its SQLite open sets and verifies WAL and `synchronous=FULL` and reads the engine's autocheckpoint threshold. The normal runtime neither caps the physical page image nor truncates the WAL on a verified schedule. At the observed 4,096-byte page size, 1,000 frames occupy about 3.93 MiB including WAL headers. This is the point that triggers a checkpoint attempt. A long read transaction can pin the checkpoint and let the WAL accumulate successive page versions while ordinary commits continue. A normal inspection ends its snapshot before returning, but `policy plan` can hold a live snapshot during SQLite checks, inventory scans and hashing. The main file can retain free pages after logical collection. A full shared filesystem can stall or fail writes. The transaction path reports an uncertain outcome when the commit fails. Measure main and WAL high-water marks on the target, end diagnostic snapshots promptly and reserve data space separately from logs and backups. **P1 · Required logging can interrupt a healthy writer.** Each event stream has a 2,048-byte record limit and two segments of at most 16 MiB each. Both launchers create and retain a fresh run directory on every attempt. Their default paths put the log and DB on the same filesystem, so log space across restarts depends on operator retention. The CLI requires the event path. A write or rotation error reaches `events_unavailable` from ordinary reactor paths, and rotation takes the shared event mutex across synchronous file I/O. A full or stalled log filesystem can therefore stop or block the reactor even when the DB has space. Enforce total retention of closed runs and provision space for two active segments plus inodes. For a dedicated service, locate events on a managed, distinct path and monitor that sink and the writer. A product fix would isolate logging backpressure and explicitly define recovery when observation is unavailable. **P1 · A database near the offline ceiling can commit a transition it cannot confirm.** `policy plan` and `apply` require secure schema 13 and accept a committed `page_count × page_size` up to 128 MiB inclusive, 32,768 pages at 4 KiB. Freelist pages count. The 32 MiB logical snapshot and the 65,536-row and 8 MiB field limits are separate. The plan JSON has its own 2 MiB limit. An operator can run a DB outside the offline page-image cap and receive `capacity_exceeded` when onboarding. At or just below the cap, if inserting owners needs a new page and crosses the cap, `apply` can commit the new authority, then return `Unknown` with `readback_failed`. A retry then refuses `capacity_exceeded` before it reaches `AlreadyApplied`. This follows from the checks around commit. I did not establish that the ordinary pilot workload reaches this boundary. Check the staged page image before commit and fail without changing authority if it exceeds the ceiling. Until then, leave measurable space below the ceiling and rehearse on a validated stopped-state copy if close to it. [Offline cap and typed refusal](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/policy_transition.rs#L118) · [Backup and apply checks](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/policy_transition.rs#L516) · [Commit and readback](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/policy_transition.rs#L545) · [Snapshot budget](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-api/src/lib.rs#L130) · [Plan byte limit](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/policy_transition.rs#L17)

**P2 · The normal retry confirms authority but cannot reissue the backup attestation.** If `apply` commits and its output is lost, `AlreadyApplied` confirms the new authority and the planned business fingerprint. That branch does not inspect the requested backup or return its hash. The restore guide requires the hash emitted by the first `Applied` result. Capture it separately from the backed-up filesystem. If the result was lost, verify the candidate backup using read-only `policy plan` with the old identities and compare the full business fingerprint and inventory with the original plan before recording a fresh file checksum. A durable backup manifest containing the original basename, digest and plan identity would make this recovery direct. [Early retry return](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/policy_transition.rs#L529) · [CLI output](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/policy_transition.rs#L328) · [Restore instructions](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/preview/POLICY.md#L82)

**P1 guard gap outside canonical-path pilot · An adjacent lease does not unify file aliases.** The broker uses the raw `--db` path to name the lock. A final symlink can reach the same database via SQLite's Unix pathname resolution while using a different lock name. The offline tool rejects final symlinks and multiply linked DB files and then uses the real adjacent path, so identical lock semantics depend on both processes selecting the real path from the outset. A second broker opening a new epoch can retire the first broker's live epoch and perform restart cleanup while that first process still has connected clients. SQLite transactions and epoch checks constrain the effects. The existing writer-lock test covers two processes with the identical path. Use a single real pathname throughout the pilot and preserve its lock inode. Enforce the same path checks in both entry points to close the gap. Network filesystems and uncoordinated SQLite writers remain outside the lease contract. [Lease implementation](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/lib.rs#L1351) · [Broker open flags](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/lib.rs#L1596) · [Offline path checks](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/policy_transition.rs#L100) · [Epoch-opening cleanup](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/lib.rs#L2684) · [Exact-path writer test](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/tests/writer_lock.rs#L172) · [Documented lease scope](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/docs/decisions/0036-offline-monotone-policy.md#L46)

**P0 impact conditional on a colliding direct CLI configuration · Event files can overlap SQLite files.** The active event output is opened exclusively and written before SQLite starts. A direct CLI configuration can name an initially absent SQLite sidecar as that output. JSON and SQLite can then use the same file. In particular, SQLite's WAL checkpoint takes page data from offsets in the WAL and writes those bytes back to the database, so a second ordinary file descriptor writing there breaks the integrity assumptions around committed state. Rotation also renames onto its `.previous` destination without verifying that it remained disjoint from the DB files. The packaged launchers place logs in fresh child directories and exclude this overlap under their normal private-directory use. Treat this as a configuration hazard identified from source. Reject overlaps for both event destinations against the DB, sidecars and lease before opening the event stream, and keep event outputs in a separate private directory for the pilot. **P2 · Published compatibility language needs to name the current formats and ELF floor.** The archive's main README says schema 10 only. The executable uses plaintext schema 12 and secure schema 13. These are separate formats, and older versions and cross-profile opens are refused. Align the README and older current-tense statements in the product guide, and document the runtime dependency floor below. A rollout over existing schema 10 or 11 requires a separate migration decision. ## Pilot operating criteria

- **Host and memory.** Use the exact CI archive on glibc Linux x86-64. Verify a clean start and stop on the target host image, including the container's `CLOCK_BOOTTIME` behavior if applicable. The observed structural limits are 16 active or retiring connections, 8 simultaneous unauthenticated handshakes, 65,536-byte MQTT packets, 4 input and 4 output items per connection, 32 writer requests, 16 commands in flight and 512 timers. There are 128 sessions and subscriptions, 8 filters per request, 16 destinations per publish, 4 MiB shared durable payload, 128 references and 8,192 receipts. Retained state and Wills have their own allowances, including 32 retained topics and 1 MiB of current retained bytes, 256 Will intentions with 8 MiB of payload, and 8 MiB of canonical Will-open receipts. These bounds govern objects, fields or copied data. Measure peak RSS, file descriptors and threads on the target under its expected clients, backlog and restart before setting process limits. Time-domain recognition is independent of the ELF ABI. A changed or unrecognized BOOTTIME domain can quarantine old expiring messages. [Runtime constants](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L49) · [Transport and readiness](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/runtime.rs#L4722) · [Writer quotas](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/writer.rs#L57) · [Will receipt limit](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/will.rs#L461) · [BOOTTIME provider](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/session_time.rs#L56) · [Expiry continuity behavior](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/preview/README.md#L110)
- **Disk.** Place the canonical DB, transient sidecars and permanent lease on one private local filesystem and budget main-file high-water plus peak WAL and SHM, filesystem reserve, transient SQLite writes and enough free inodes. Measure them along with available space and actual checkpoint progress. Treat the 128 MiB policy cap as an upper bound for the committed image considered for that operation. It provides neither a bound for the live database/WAL footprint nor backup volume capacity. Provision another full page image plus transient journal and write headroom for each backup in progress and room for an independent restore copy and retained snapshots. For launchers, budget up to 32 MiB per retained run, including the active run. Prune or export only inactive run directories. An operator can put logs and backups on separate volumes to preserve write and checkpoint headroom for SQLite. [Live SQLite settings](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/lib.rs#L1400) · [Policy image check](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/policy_transition.rs#L118) · [Backup copy path](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd-store-sqlite/src/policy_transition.rs#L395) · [Log rotation](https://github.com/yoch/mqttium/blob/49bbaaa4d1d080f458980e3498e90638e317668d/mqttiumd/crates/mqttiumd/src/events.rs#L51)
- **Normal stop and restart.** Send SIGTERM or SIGINT and wait for exit. For a normal running service require exit 0, `session_shutdown_completed` and `stopped` with `writer_released=true`, and investigate typed failure or `shutdown_incomplete` before declaring success. The code provides successive 2-second session and socket budgets and a 5-second writer join budget. These are runtime checks around work and waiting. A blocking syscall can delay them. `stopped` does not prove a complete checkpoint when another SQLite connection remains open. SQLite can checkpoint and unlink WAL/SHM on the last close if it obtains the needed lock. Preserve the original files and sidecars for same-path restart, especially after a kill. Check `sqlite_configuration` and `ready`, the expected incarnation and an advanced epoch, and resume a known persistent subscription and retained value as acceptance checks. Pending Wills can be reconciled on restart. SIGKILL and successful restarts establish process-level evidence. The pilot has no filesystem or power-loss certification. - **Backup and restore.** For recurring backups use a coherent SQLite snapshot, such as the SQLite backup API, and verify the standalone image. A live copy of the main file can omit committed WAL state. The secure offline tool's explicit flow is to stop the broker and other writers, keep the original identities, make a fresh plan, and apply to the same canonical DB using a new regular backup destination in a private directory. The tool takes the lease, freezes an SQL read snapshot, copies with the SQLite backup API, returns the destination to DELETE journal mode, verifies schema, old authority, integrity and business fingerprint, then closes and syncs the copy. It publishes it by a non-replacing hard link and directory sync before opening the authority transaction. Keep the `Applied` receipt, old config and matching credentials with the backup. Verify the file SHA-256 and integrity, copy to a new private directory with a fresh sidecar namespace, and rehearse startup there with the old identities. Verify the expected retained value and outstanding persistent QoS 1 deliveries. Preserve the current data set with its sidecars and route clients to only one chosen point-in-time copy.
